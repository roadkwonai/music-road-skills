# 프로젝트 성능·스타일·레퍼런스 UI 검수 (2026-10-19)

## 적용 결과

- 제작 분석의 기본 화면을 프로젝트별 음악/영상/전체 누적 시간·성공 평균·요청/생성/수정 횟수 비교표로 변경했다. 검색·작업 영역·불러온 행 정렬·초기화와 기존 cursor/무한 스크롤을 유지하고, 전체 집계·일별/유형 그래프는 펼쳐 보기로 옮겼다.
- 내 작업물 목록에는 음악 그룹의 전체·음악·영상 누적 시간을, 그룹 상세 요약에는 과정별 시간 파이와 전체 범례를 추가했다. 비중 12% 이상인 주요 과정 최대4개는 파이 안에 이름/비율을 표시한다. 작은 과정은 범례에서 정확한 시간과 <0.1%까지 확인한다.
- 성능 값은 기존 SQLite에서 상위 작업만 집계한다. 실패·취소 실측은 누적에 포함하고 평균은 성공 실측만 사용한다. 미측정 null과 실제0을 보존한다. 작업물 목록은 그룹100개 단위의 단일 SQL 배치로 조회해 그룹마다 다시 질의하지 않는다. CLI `production:projects.performance`와 `production:dashboard.groupIds/groupSummaries/stageBreakdown`도 반영했다.
- 스타일 미리보기 7개의 기존 대표 JPEG를 인증 미디어 경로로 연결했다. 검색·제작 스타일·장르 방향·장르 태그를 AND로 적용하며 카드 태그 선택, 전체 초기화, 결과/빈 상태와 URL 조건 복원을 제공한다. 장르 방향은 접어 두고 중립 태그 칩만 선택 상태를 강조한다. 새 이미지 생성·영상 렌더는 하지 않았다.
- 공개 명령190개와 활용 참고45개를 구분했다. 실제 스키마 악기37개를 개별 카드로 만들고 카테고리·태그·검색, 사용/피할 상황·예상 효과·복사 예시를 제공한다. 주요 명령7개에는 실제 입력 예시와 예상 응답·관련 가이드를 추가했다. 예시는 자동 실행하지 않으며 생성 결과를 보장하지 않는다.
- 환경 상태는 최대6개 핵심 항목과 160자 값으로 제한하고, 요약 높이240px·원문 펼침320px로 긴 응답을 카드 안에서 확인하게 했다.

## 실제 확인

기존 실제 제작 샘플의 SQLite와 보관함을 별도 프로필에서 재사용했다. 새 모델 추론이나 샘플 파일 변경은 없었다.

- 프로젝트 검색의 빈 결과, 음악 영역1행/초기화3행, 시간 정렬, 프롬프트·결과 모달을 실제 Ego에서 확인했다.
- 음악 그룹 누적10.9분(음악1.5분/영상9.4분), 파이7개 과정, 내부 글씨3개(음악 생성13.3%, 이미지 생성22.6%, 영상 렌더62.2%)를 확인했다.
- 7개 대표 이미지를 브라우저에서 실제 decode했다. CD+인디 밴드1/7, 재로드 조건 복원, 없는 검색0/7, 전체 초기화7/7, 카드 칩 선택을 확인했다.
- 레퍼런스 악기+건반6/45, 예시 복사 성공, 빈 검색 결과, 전체 선택을 확인했다.
- 상태 카드 기본 높이314px, 기본 펼침0개, 원문 max-height320px를 확인했다.
- 데스크톱1280px와 모바일390px에서 기능/화면을 점검했다. 새 표는 영역 안에서 가로 이동하며 페이지 가로 넘침은 없었다. Paperlogy 로딩도 확인했다.

## 검수 중 보완한 결함

1. 공유 성능 UI보다 소비 스크립트가 먼저 로딩되는 순서 문제를 고쳤다.
2. 완료 정리의 최소 메타 허용 목록에서 스타일·원음·자막 대응·제작 시각이 누락돼 재등록 시 사라지는 문제를 고쳤다. 이미 과거에 사라진 값은 추정 복원하지 않았다.
3. HTML에 CSS 선택자 `data-road-music-ui` 문자열이 있다는 이유로 실제 html 속성을 생략하던 공통 렌더러를 Python/Node 양쪽에서 고쳤다. 생성 카탈로그에 실제 속성·28px 태그 칩·공통 디자인이 적용됨을 확인했다.
4. 카탈로그 poster.jpg 상대 URL 변환 누락과 레퍼런스 가이드 fragment 앞의 인증 쿼리 위치를 고쳤다.
