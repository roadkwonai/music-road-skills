# Road Music 제작 기록

프로젝트별로 최초 사용자 요청을 메인 프롬프트로 보존하고, 뒤이은 수정 요청·실제 제작 시간·AI 응답 요약·결과 파일을 프로필 `storage.sqlite3`에 연결한다. 미디어·프레임·엔진 로그 본문은 복제하지 않는다.

## 기록할 때

- 새 음악 또는 모션그래픽 제작을 시작하기 전, 사용자 요청마다 `production:request`를 한 번 기록한다. 같은 프로젝트·분야의 첫 제작 요청(`source:"user"`)은 메인 프롬프트가 된다. 기존 곡의 제목·가사 수정부터 기록했다면 과거 최초 제작 원문을 추측해 메인으로 삼지 않는다.
- 제목·가사·음악·영상·연출을 수정하라는 새 사용자 요청도 새 `requestId`로 기록한다. 엔진이 내부적으로 만든 문구는 같은 요청을 다시 저장하지 말고 `source:"engine"`으로 필요한 경우에만 남긴다.
- 실제 생성·렌더·분석 작업은 받은 `requestId`를 `production:task-start`에 연결하고, 종료 시 같은 `taskId`로 `production:task-finish`를 한 번 실행한다. 시작 시 이미 확인한 길이·프레임만 기대값으로 기록하고, 실행 중에는 실제 producer 단계 경계만 `production:task-progress`에 저빈도로 기록한다. 파일은 실제 생성·확인한 경로만 역할별로 연결한다.
- 작업이 시작되지 않았거나 파일·측정값을 확인할 수 없으면 추정값을 만들지 않는다. `elapsedMs`, `mediaSeconds`, `frameCount`는 모르면 생략하고 HTML에서 알 수 없음으로 보이게 한다.

초기 요청과 수정 이력, 프로젝트별 횟수, 평균·느린 작업 비교, 파일 목록은 HTML 작업물 상세와 대시보드에서 조회한다. 상세한 입력·출력 형식과 비교 조건은 [원장 기록 계약](references/ledger.md)을 읽는다.

## 내장 제작 경로와 중복 방지

새 폴더를 배정하는 `song:generate`·`song:render`·`song:replay`는 최초 원문을 `requestPrompt`로 전달하면 내장 경로가 실제 곡 폴더를 확정한 뒤 기록한다. 미리 만든 다른 프로젝트의 `requestId`를 억지로 전달하지 않는다. 생성 응답의 `production.project`, `requestId`, `taskId`를 이후 기록에 사용한다. 이미 같은 프로젝트에 기록한 요청만 같은 ID로 재사용한다.

내장 생성·수정·Showreel/JIZURA가 자동으로 기록하는 작업을 스킬에서 다시 task로 세지 않는다. 결과 검수와 완료 응답을 정리하는 실제 단계는 같은 `requestId`에 `taskType:"review"`로 연결하고 `aiSummary`에 요청에 대한 응답, `resultSummary`에 얻은 결과·남은 한계를 간결하게 남긴다. 실제 검수 시간만 측정하며, 이미 종료된 생성 task의 결과를 덮어쓰지 않는다. 내장 경로 밖의 이미지 생성(`image_gen`)·기획·외부 제작 단계는 원문/엔진 입력을 구분해 별도 task를 기록하고, 실제 걸린 시간·생성 파일·간결한 AI 응답을 연결한다. 알 수 없는 모델명·실측값은 만들지 않는다.

## 조회와 업데이트

`production:projects`, `production:prompts`, `production:tasks`, `production:files`는 cursor 기반 페이지 조회이며 대시보드는 전체 필터 범위를 SQL로 집계한다. 먼저 반환된 `nextCursor`가 있을 때만 다음 페이지를 요청한다. 목록 전체를 한 번에 읽거나 각 화면 이동마다 전체 파일을 재스캔하지 않는다.

`production:components`는 관찰한 앱·CLI·스킬 묶음 버전과 마지막 확인 시각을 보여 준다. 업데이트 스킬의 SQLite 기록은 알림과 비교용이며, 실제 설치 성공은 항상 현재 설치본의 manifest/버전·체크섬·검증 결과로만 판단한다. 확인만으로 다운로드·설치·재시작하지 않는다.

프로젝트·음악 그룹을 공개 저장공간 절차로 제거하면 연결된 원장 라이브 행도 함께 제거된다. 원음·최종 납품·모델을 일반 기록 삭제 대상으로 취급하지 않는다.

그룹 상세에서 이 음악의 요청·결과를 볼 때는 보관함이 반환한 `groupId`를 `production:prompts/tasks/files`에 전달한다. 제목으로 다른 그룹을 추측해 합치지 않는다. 좋아요는 공개 `works:list`·`works:favorite`로 관리하며 보존 핀이나 파일 삭제 권한으로 해석하지 않는다. HTML 업데이트 버튼은 기존 공개 업데이터로만 연결하고 확인·진행·완료 또는 설치 미확정을 구분한다.

## 음악 그룹 경계

한 프로젝트 경로는 귀속된 음악 그룹을 보존한다. 다른 non-null `groupId`로 기록하면 명시 오류가 나므로 새 음악에는 새 프로젝트를 사용하고 기존 이력을 임의 재귀속하지 않는다. 요청·엔진 입력·부모 작업·재사용 taskId의 그룹도 일치해야 한다. 조회 API는 메인 요청을 전체 요청에도 포함하므로, HTML의 추가 요청 목록에서만 `main`을 제외하며 집계 수는 원장 그대로 유지한다.

음악 생성이 성공하면 실제 최종 음원 SHA-256으로 미귀속 기록을 같은 음악 그룹에 연결한다. 첫 귀속은 기존 null 프롬프트·하위 작업·파일에도 적용하며 이미 귀속된 다른 그룹은 덮지 않는다. 완료 음원이 있는데 그룹 상세에서 음악 기록이 빠졌다면 실제 파일 해시와 기존 requestId를 확인하고 같은 원문·ID의 공개 `production:request`로 첫 연결만 복구한다. 새 요청·작업을 중복 생성하거나 과거 측정값을 바꾸지 않는다.

프로젝트 성능 비교는 `production:projects`의 페이지별 `performance`를 사용한다. 음악 그룹별 시간·과정 비중에는 `production:dashboard`의 `groupSummaries`·명시 단일 그룹 `stageBreakdown`을 사용하며, 여러 그룹은 최대100개 `groupIds`로 묶어 조회한다. 상위 작업의 실측 누적과 성공 평균을 구분하고 하위 단계·미측정 시간을 임의 합산하지 않는다. 누적 작업 시간을 최초 요청부터 완료까지의 경과 시간으로 설명하지 않는다.

진행·대기열 화면은 `production:activity`를 사용한다. 예상 시간은 같은 domain·taskType·engine·model의 실제 성공 기록이 있을 때만 표시하며, 표본이 없으면 알 수 없음으로 남긴다. 앱 메모리 음악 큐는 `queue:list --no-start`로만 읽고, 앱이 꺼져 있으면 오프라인으로 표시하며 자동 시작하지 않는다.

진행률은 현재 요청의 상위 작업 예상 진행률과 엔진의 실제 단계 비율을 구분한다. 등록된 다음 대기 작업만 총시간에 포함하고, 과거 흐름으로 추정한 단계는 예약으로 취급하지 않는다. 그룹 조회도 전체 실행 순서에서 앞선 다른 작업의 대기 시간을 반영한다. 예상 초과·표본 없음·일시정지·오프라인·순서 미확인에는 부분합과 불확정 상태를 유지한다. 진행 기록을 위해 실제 생성·렌더 작업을 중복 등록하거나 매 프레임 SQLite에 쓰지 않는다.
