# Showreel 모션 스코어

전곡 M/V에서 Showreel의 표현 수단을 곡의 장르·가사·편곡에 맞춰 고를 때 읽는다. 이 문서는 새 엔진 API나 프리셋이 아니다. 설치본 Showreel의 `engine.md`·`design.md`·`techniques.md`·`qa.md`를 실제 제작 시 함께 확인해, 보드의 단어가 실제 장면 코드와 검수 증거로 이어지게 한다.

2026-10-18 공식 원격/설치본에서 확인한 commit은 `64521220a2f8e91cb9894400c48c15b7f45205d6`이다. 공식 [기법 원문](https://github.com/revfactory/showreel/blob/64521220a2f8e91cb9894400c48c15b7f45205d6/references/techniques.md), [엔진](https://github.com/revfactory/showreel/blob/64521220a2f8e91cb9894400c48c15b7f45205d6/references/engine.md), [디자인](https://github.com/revfactory/showreel/blob/64521220a2f8e91cb9894400c48c15b7f45205d6/references/design.md), [비평·QA](https://github.com/revfactory/showreel/blob/64521220a2f8e91cb9894400c48c15b7f45205d6/references/qa.md)가 근거다. 이후 작업은 실제 설치본 API를 확인하며 조사만으로 자동 업데이트하지 않는다.

공식 `brief.md`의 콘셉트 비교와 `story.md`의 음악 기반 구성·보드·`script.json.scenes`를 필요한 단계에서 읽는다. `images.md`는 이미지 후처리/시트, `audio.md`는 분석·믹스 또는 명시된 사운드 디자인에 쓰는 절을 읽는다. 홍보 영상의 나레이션 분량·가상 의뢰·CTA 예제를 완성곡 M/V에 강제하거나 가사를 원고 검토 명목으로 바꾸지 않는다.

## 콘셉트와 선택

연출이 위임됐을 때만 실현 가능한 대안 2~3개를 짧게 비교한다. 각 대안은 가사의 관점·음색/리듬 단서·주 매체·인물 필요 여부·후렴의 변화가 달라야 한다. 선택한 안의 이유와 버린 안을 남긴다. 사용자가 확정한 콘셉트, 장르, 참고 미술, 폰트, 인물/무인물, 자막 방식은 다시 후보로 만들지 않고 그 범위 안에서 모션을 설계한다.

장르표는 효과 배정표가 아니다. 예를 들어 드롭이 있는 전자음악에는 저역·대역 변화가 보이는 기하/공간 변형이 어울릴 수 있고, 보컬 프레이즈가 중심인 R&B에는 미세한 잔광·거리 변화가 더 맞을 수 있다. 이는 관찰된 음악 단서와 가사 정서가 뒷받침할 때의 선택이며, 모든 구간에 다른 매체를 쓰거나 모든 기법을 쓰라는 뜻은 아니다. 한 매체의 일관성이 작품의 핵심이면 색·카메라·물성·운동 상태의 변화만으로 전개해도 된다.

## 보드에 붙이는 모션 스코어

기존 전곡 보드의 각 행을 확장하거나 별도 표를 둔다. JSON schema나 엔진 API로 오해하지 않도록 사람이 읽는 제작 기록으로 유지한다.

| 기록할 것 | 필요한 내용 |
| --- | --- |
| source/output 시계 | 원곡 시각과 출력 시각, 둘이 다르면 offset/편집 이유. 임의 숫자보다 `scene.*`, `music.hit*`, `line.*` 같은 이름 붙인 cue를 우선한다. |
| 음악·가사 근거 | 들린/측정된 다운비트·히트·프레이즈·에너지, 확정 가사와 정서 전환. 추정은 추정으로 표시한다. |
| 화면 과제 | 장면의 메시지, 매체(DOM·SVG·Canvas·사진·WebGL 등), 물성, 운동, 인물/공간과 레이어 우선순위. |
| 기법과 구현 | 선택한 T01–T22 또는 새 기법, 실제 파일/`REEL.scene`/함수 또는 `FX.*` 호출 경로. 이름만 적고 구현하지 않는다. |
| 시간 동작 | 진입 → 정착 → 전개 → 퇴장, 컷/와이프/매치 연결, 정착 전에 읽혀야 할 글자와 자막의 안전 영역. |
| 증거 | 스타일 프레임, cue 전후 프레임 띠, 원음 proof 구간, 약점 및 keep/fix/rebuild 판정. |

이전 프로젝트의 절대 원음 경로도 내용이 바뀔 수 있다. 기록된 SHA256과 현재 파일을 다시 대조하고 불일치하면 같은 해시의 보존 원본을 찾거나 현재 음원용 정렬을 새로 검증한다. 기존 자막의 해시만 바꿔 연결 검사를 우회하지 않는다.

하드 컷과 상태 전환은 `cue - 0.5/fps`를 적용해 `--sub 4` 셔터에서 새 상태가 cue 프레임에 처음 보이게 한다. 가창 자막 onset에는 그 보정을 기계적으로 적용하지 않는다. source/output 시계가 달라지면 원곡·SRT·가사 cue·박·FFT·장면 cue의 공통 offset을 함께 기록하고 검증한다.

## 실제 Showreel 구현 선택

`REEL.scene({ id, start, end, setup, render })` 하나가 보드의 장면 하나를 담당한다. DOM/SVG/Canvas는 `setup`에서 만들고 `render(lt, ctx)`에서는 시간에 따른 스타일·그리기만 갱신한다. `Math.random()`, 실시간 clock, CSS animation/transition, 누적 프레임 상태를 쓰지 않는다. 이미지·폰트·로컬 라이브러리는 준비가 끝난 뒤에 렌더하며, 외부 CDN에 의존하지 않는다.

새 씬의 부트 순서는 `timeline.js` → 자체 가사/큐 데이터 → `engine.js` → 선택 `fx.js` → `scenes.js`다. 엔진은 로드할 때 `window.TL`을 캡처하므로 타임라인을 뒤에 불러오면 큐·음악이 빈 객체로 고정될 수 있다. `REEL.config`는 프로젝트 duration/fps/audio와 일치시켜 한 번 설정한다. 쓰는 named cue의 존재·유한값·범위를 확인하고, 없는 cue가 0초로 대체된 경고를 통과시키지 않는다. `script.json.scenes`는 `timeline.py`로 양쪽 타임라인에 반영하며 임의 top-level `script.json.cues`를 지원한다고 가정하지 않는다. 추가 구절 큐는 최종 `timeline.json`과 `reel/timeline.js`의 cues에 동일하게 기록하고 생성 근거를 보존한다.

`REEL.img()`는 호출 시 이미지와 preload 대기를 등록하므로 setup 이전 완료를 가정하지 않는다. 픽셀/자연 크기를 읽는 마스크·입자 캐시는 async setup에서 실제 decode·유효한 크기를 확인한 뒤 만든다. 엔진이 로드 실패를 로그만 남기고 진행할 수 있으므로 필수 자산 실패를 프로젝트에서 명시적으로 거부한다.

- 타이포·마스크·선·카드에는 DOM/SVG, 입자·절차형 패턴에는 Canvas 2D를 먼저 쓴다.
- 깊이, 반사, 셰이더가 장면의 의미를 실제로 바꿀 때만 WebGL2 또는 `reel/lib/`의 로컬 three.js를 쓴다. three.js의 시간은 `mixer.setTime(lt)`처럼 명시한다.
- 충돌·천·입자처럼 이전 상태가 필요한 운동은 `setup`에서 결정적으로 사전 계산하고, `render`는 해당 시각을 읽어 보간한다.
- 전역 효과는 실제 설치본에 있는 `FX.camera`, `FX.impact`, `FX.wipe`, `FX.floor`, `FX.dust`, `FX.rays`, `FX.flash`, `FX.leak`, `FX.letterbox`, `FX.vignette`, `FX.grain`, `FX.hud`, `FX.subtitles` 중 필요한 것만 쓴다. 호출 순서가 레이어 순서다.

`FX`는 `engine.js`만으로 생기지 않으므로 새 프로젝트의 `fx.js` 로드를 확인한다. 실제 `assets/engine/fx.js`에서 `camera`의 shakes/zoom/whips/beat, `wipe`의 slats/bars 등 인자를 확인한다. floor/dust/rays는 불투명 장면 아래에 가려질 수 있는 back 레이어다. WebGL2는 `preserveDrawingBuffer:true`와 render마다 실제 draw·셰이더 compile/link 확인이 필요하다. 원래 사진은 평면이며 2.5D 효과를 실제 연속 연기나 3D 인물 생성으로 보고하지 않는다.

T01–T22는 내장 enum도 품질 체크리스트도 아닌 검증된 코드 조각이다. 기법은 곡의 과제를 해결할 때만 변형해 쓴다. T17은 절차적 김·연기를 설명하는 기법이며, 장르를 뜻하거나 반드시 포함할 항목이 아니다. 새로운 기법은 같은 결정성·큐·첫 프레임·섬광 규칙과 실제 proof를 가진다면 사용할 수 있다.

선택한 기법의 절을 실제로 읽고 적용한다. 다음은 장르 고정값이 아닌 활용 후보다.

| 음악·가사의 시각 과제 | 원문의 기법 범위 | M/V 적용과 확인 |
| --- | --- | --- |
| 도시·시간·초점이 변하는 공간 | T01 복셀 도시, T02 낮→밤, T03 틸트시프트/모핑 | 도시/시간이 실제 주제일 때 사용하고 공간·광원·초점의 변화를 proof |
| 말·기억·관계가 흩어지고 이어짐 | T04 입자, T05 자모, T06 가변 굵기 | 장식 활자와 즉시 읽히는 가사를 구분, 폰트 축과 원문 유지 |
| 타격감·금속/빛의 재질 | T07 슬램, T08 유리·크롬, T09 프리즘 | 실제 악센트와 반사·무게·정착을 연결, 전면 섬광 대신 조형 변화 |
| 디지털 신호·분절·메시지 | T10 타일, T11 데이터 맥박, T12 카운터, T13 픽셀 분해, T14 3D 기기 | 의미 있는 소품/실제 데이터만 사용, UI나 수치를 가짜 사실로 만들지 않음 |
| 시선·심도·호흡의 연결 | T15 펀치 인, T16 매치 컷/패럴랙스, T17 김·연기 | 앞 장면의 형태·방향을 이어받고 사진 과도한 분해/뒤틀림 방지 |
| 편곡의 전환·절정·여운 | T18 비트 몽타주, T19 잔상, T20 안전 리듬, T21 디더/그레인, T22 엔드카드 | 훅은 변주하고 읽기/호흡으로 복귀, 질감/크레딧 상시 강제 금지 |

## 음악·자막의 경계

이 스킬의 기본은 제공된 완성곡의 원음 시계를 보존하는 것이다. 생성 음악, BPM/피치 변경, 구간 splice, TTS, 효과음 더빙은 기본 제작 단계가 아니다. 사용자가 명시적으로 사운드 디자인을 요청한 경우에만 설치본 `audio.md`의 기능을 검토하고, 원곡/변경본·큐·믹스 영향·검수 범위를 분리해 기록한다.

별도 유료 API/모델은 이 스킬의 명시 요청 경계를 그대로 따른다. 공식 데모의 음성 4종·생성 음악·SFX는 그 작품의 구성이다. 기존 음악 M/V의 필수 요소가 아니다. 음악 분석의 beats/downbeats는 고정 BPM·4박 추정이며 genre/가창/변박 검출 결과가 아니다. `level`은 에너지이고 실제 FFT 대역과 다르다.

가사 전체는 onset에 읽을 수 있어야 한다. 장식용 글자 등장이나 `charTimes`의 균등 분할은 실제 한국어 음절/단어 가창 시각이 아니다. 검증된 word/음절 timestamp가 없으면 가라오케 강조나 단어별 싱크를 주장하지 않는다. 제목·자막·그래픽의 운동은 가창을 가리거나 늦추지 않으며, 조용한 구간을 억지 효과로 채우지 않는다.

## proof와 재제작 판정

구간마다 먼저 스타일 프레임을 만들고, 시작+0.5초·핵심 cue+0.4초·끝-0.6초와 전환/임팩트 주변의 연속 시간 띠를 본다. 이어서 각 주요 연출을 대표하는 약 10–15초 원음 proof를 보고, 전곡 렌더 전에 약한 구간만 고친다.

설치본 `qa.md`의 여덟 질문을 구간별로 판단하고 `qa/critique_NN.md`에 `keep`, `fix`, `rebuild`와 이유를 기록한다.

1. 다른 템플릿/AI 영상 옆에서 이 곡만의 디자인으로 구분되는가?
2. 구간별 전개가 보이는가? 작품의 일관성 안에서 매체·색·거리·운동 상태가 필요한 만큼 변하는가?
3. 선택한 기술적 과제가 기억에 남는 순간을 만드는가?
4. 한글 조형이 필요한 작품에서 글자의 구조를 쓰는가? 비문자 작품이면 N/A 이유를 적고 문구를 억지로 넣지 않는다.
5. 시간 띠에서 예비 동작·넘침·겹침·후속 동작의 무게와 재질이 보이는가?
6. 화면과 실제 음악이 같은 리듬이며 사건 크기·간격에 대비가 있는가?
7. 반복·전환이 다음 장면을 너무 쉽게 예상하게 만들지 않는가?
8. 가장 약한 구간은 어디이며 무엇을 고치거나 다시 만들 것인가?

`fix`는 수치·레이어·큐를 조정해 다시 proof한다. `rebuild`는 장면의 매체/운동/구성을 바꾸고 이전과 같은 시각을 비교한다. 기술 검수 통과나 모든 항목의 `keep`은 사용자 취향의 보증이나 모든 장르에 대한 품질 보증이 아니다.

이 비평과 별도로 첫 프레임·가사 onset 전후·퇴장·곡/컷 경계 ±3프레임, 원음/자막/FFT의 시계, 폰트·레이어 겹침, 역순 seek를 검사한다. 렌더된 사진/효과/가사가 모션 스코어의 구현과 일치해야 한다. `motion_check.py`와 완성본 `qa_check.py`를 실행하고 최종과 같은 `--sub 4`에서도 섬광·잔상을 확인한다. 의도한 정착 경고는 구간/음악 근거를 보고하며 섬광 실패나 임계값 하향으로 해결하지 않는다. 자동 검사는 한글 오탈자·폰트 대체·겹침·노래 가사 정답을 보증하지 않으므로 실제 시트/원음 proof와 독립 시각 검토로 보완한다. 청취·정렬을 하지 않았다면 그 범위를 명시한다.
