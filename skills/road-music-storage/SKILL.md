# 제작물을 지키는 저장공간 관리

## 제작 기록

프로젝트별 요청·성능·파일 이력은 [제작 기록 스킬](../road-music-production-records/SKILL.md)의 SQLite 원장을 사용한다. 일반 캐시 정리는 이 원장이나 최종 결과를 삭제하지 않으며, 프로젝트·음악 그룹 제거가 성공했을 때만 연결된 라이브 이력을 함께 정리한다.

음악·영상 제작과 수정에는 음악별 프로젝트의 저장공간을 함께 관리한다. 일반 캐시 정리에서 현재 프로그램, 설치 모델, 원음·원가사, 완성 파일, 편집 소스·승인 자산·검수 의견을 보호한다. 사용자가 AI M/V 프로젝트 전체 삭제를 명시한 경우에는 아래 전용 절차로 해당 프로젝트의 영상 완성본·애니매틱·중간본까지 포함한다. 원본 음악과 모델을 지우라는 권한으로 확대하지 않는다. 이 스킬은 제작 엔진과 연출 결정을 바꾸지 않는다.

## 시작과 수정

- 현재 설치본의 `node /absolute/road-music/cli/road-music.js schema --json '{"command":"storage:register"}'`와 `storage:list`를 확인한다. 앱 실행 없이 동작하는 명령이다. 명령이 없으면 해당 기능의 미설치 상태를 알리고 임의 셸 삭제로 대체하지 않는다.
- 알려진 Road Music 프로젝트 표지를 가진 실제 프로젝트 경로나 공개 도구가 확인한 현재 trusted Road Music workspace root를 `storage:register`로 등록하고 반환한 ID를 사용한다. 같은 대상을 다시 다룰 때에는 같은 등록 ID를 재사용한다. 매 수정마다 앱·저장소·모델·완성 폴더를 복제하지 않는다.
- 기본 상태는 `editing`, `preserveHistory:true`다. 작업 중 보존이 필요하면 해당 프로젝트의 `autoCleanup:false`를 저장한다. 보존해야 하는 중간본은 `storage:pin`으로 고정하고 새 작업에서도 핀을 유지한다.
- 재생성 가능한 자료는 `.roadmusic/cache/`, 비교용 중간본은 `.roadmusic/intermediate/`, 상세 히스토리는 `.roadmusic/history/` 아래에 따로 만든다. 최소 제작·정리 요약 `.roadmusic/history.jsonl`은 별도로 보존한다. 기존 프로젝트 자료를 자동으로 이 경로에 이동하지 않는다. 관리 등록은 분류에 맞는 전용 폴더 안에서만 가능하다.
- 새 음악·영상 producer의 작업 루트는 `.roadmusic/work/<원음SHA12 또는 unassigned>/<프로젝트명--ID>/`다. 사용자가 새 프로젝트의 `Output/...` 경로를 준 경우 이 작업 루트로 변환한 실제 절대 경로를 이후 명령에 사용한다. 기존 경로·완성된 프로젝트·외부 경로는 조용히 옮기지 않는다. `Output/`에는 게시 검증을 통과한 완성 파일만 두고 버전 메타데이터는 `.roadmusic/history.sqlite3`에 둔다.
- 실제 생성된 경로만 `storage:track`에 등록한다. `cache`에는 재생성 가능 여부와 용도를 적는다. 이름이 cache·tmp·draft라는 이유만으로 원음·최종본·미등록 파일을 재분류하지 않는다. 이전 프로젝트 자료는 용도·현재 참조를 먼저 확인한다. 전용 폴더 밖의 원음·완성본·레거시 자료는 읽기 전용으로 남기며 캐시로 이름 붙여 삭제하지 않는다.
- workspace 등록 결과의 `usageScope:managed-cache`는 `.roadmusic` 아래 관리 항목만 집계한다. 소스·CLI·AGENTS·Git·Output 원본을 프로젝트 용량으로 다시 세거나 정리하지 않는다. 공용 `<앱 데이터>/video-cache/`는 프로젝트 레거시 후보가 아니다. 과거 앱이 살아 있으면 보존하고, 사용자가 안전 재시작·공용 캐시 정리를 요청했을 때에만 아래 전용 유지보수 경로를 따른다.
- 실제 제작 프로세스는 `storage:lease`로 작업 잠금을 잡고 `finally`에서 자기 토큰만 해제한다. CLI로 잠금을 획득할 때에는 제작 전체를 감싸는 살아 있는 프로세스의 `pid`를 명시한다. 금방 끝나는 조회/CLI 브리지의 PID를 사용하지 않는다. HTML은 작업 상태를 표시할 뿐 잠금을 강제로 풀지 않는다. 기본 Showreel 제작 경로의 내장 잠금과 중복해서 새 잠금을 만들지 않는다.
- 성공한 렌더 단계에서는 자동 정리가 켜져 있고 캐시 용량/파일 예산을 넘겼을 때에만 producer 소유 `picture` 재생성 캐시를 정리한다. 예산 이내의 캐시와 핀한 자료는 유지한다. 실패 렌더는 편집 중으로 돌아가 재개 파일을 보존한다. 이 동작은 현재 런타임의 프로젝트 정책에 따르며, 전체 용량 조회나 과거 자료 점검이 자동 정리 설정을 바꾸지 않는다.
- 단계가 끝날 때 용량·파일 수와 예산 경고를 확인한다. 원시 전 프레임 덤프, 원음·모델 재복사, 이미 끝난 렌더 청크의 중복 보관부터 방지한다. 고해상도 증거가 필요하면 필요한 구간을 검수하고 기존 제작 지침의 증거 범위를 축소하지 않는다.

## 완료와 최소 기록

완성 파일을 기존 제작실 `publish`로 같은 음악에 등록하고 재생·다운로드를 검수한다. 원음 해시·최종 manifest·선택·피드백·승인 및 제작 조건을 남긴다. HTML 검수 창 종료, 렌더 종료와 사용자의 수정 완료는 서로 다르다. 수정이 이어지는 프로젝트를 임의로 `completed`로 바꾸지 않는다.

사용자가 작업 완료를 맡겼고 필수 납품·검수까지 끝났으면 `storage:policy`로 `completed`를 기록한다. 완료 뒤에도 기본 히스토리 보존은 유지한다. 자동 정리는 완료/보관 프로젝트의 보존 기간이 지난 앱 소유 재생성 캐시에 한정된다. 진행 중 잠금·핀·원본·완성본은 제외되며, 제작 잠금 해제·제작실 시작·완료 처리 때 실행되는 정리를 상주 감시라고 설명하지 않는다.

제작실의 `publish` 완료 뒤에는 등록한 원음 SHA와 최종 MP3/영상의 해시·오디오/영상 스트림·길이가 모두 검증될 때만, 명시 기록된 `audio/mix_bed.wav`, `audio/mix_premaster.wav`, `audio/mix_vo.wav` 세 파생 WAV를 정리할 수 있다. 최종 MP3가 ACE 검증 결과여도 등록·검증 전에는 정리하지 않는다. 원음, 입력 WAV, production의 주 믹스, 사용자가 가져온 WAV, FLAC과 다른 가져온 오디오는 파생 캐시로 간주하지 않는다.

히스토리를 최소화할 때에는 요청·변경 이유·작업 시각·입력/최종 해시·검수 판정·정리 수량/용량 요약을 남긴다. 감사 이력이나 현재 편집본을 지워서 용량을 줄이지 않는다. 오래된 상세 중간 자료는 사용자가 해당 프로젝트에서 명시 선택했을 때만 정리한다.

## 게시 파일 제거와 프로젝트 마무리

사용자가 등록된 완성 파일 하나를 제거하거나 완료한 private work 프로젝트를 비우기를 요청하면 [게시 파일과 프로젝트 마무리](references/published-file-management.md)를 읽는다. 이 절차는 canonical Output·원음·현재 입력·활성 작업을 보호하며, 일반 자동 캐시 정리나 Output 구조 전환과 섞지 않는다.

## 점검과 정리

먼저 `storage:status`로 현재 설치·작업 폴더에서 실제로 가능한 검사만 확인한다. `enabled:false` 항목은 `reason`을 표시하고 검사·정리 대상으로 만들지 않는다. 상태 조회는 Electron·Git 심층 검사·전체 재스캔을 시작하지 않는다. 자세한 상태·캐시 계약은 [통합 저장공간 상태](references/inspection-status.md)를 필요할 때 읽는다.

프로젝트·음악 그룹·경로 소유권과 최소 생성/수정/게시/정리 이력은 프로필 `storage.sqlite3`에서 관리하고, 납품 버전·diff 원장은 workspace `.roadmusic/history.sqlite3`에 둔다. 실제 음악·영상·가사·엔진 JSON·승인 자산은 파일로 남기며 SQLite에 BLOB·프레임·로그를 복제하지 않는다. `storage:tracking`은 기본적으로 저장된 소유권 색인을 읽고, `refreshWorkspace:true`일 때만 명시적으로 경로·크기·수정 시각을 색인한다. 자세한 경계·제거 절차는 [SQLite 소유권 원장](references/sqlite-ownership.md)을 필요할 때 읽는다.

`storage:list`의 보호 사유와 실제 용도를 먼저 읽는다. `storage:preview`로 프로젝트 ID 또는 등록 전체의 재생성 캐시 계획을 만들고, 표시된 대상·총 용량·보호 항목을 확인한다. `storage:cleanup`은 받은 `planId`와 `--confirm`으로 실행한다. scan/preview는 정리 완료 증거가 아니며, lease·pin·파일 변경이 있으면 실행을 중단하고 새 계획으로 판단한다. 기존 계획을 수정하거나 실패한 삭제를 무조건 재실행하지 않는다.

`intermediate`/`history`는 정확한 항목 ID의 명시 선택과 프로젝트 보존 정책이 필요하다. **전체 비우기**도 보호 파일과 미등록 파일을 삭제하는 명령이 아니다. 삭제 권한은 사용자가 선택한 범위에만 적용한다. 모델·프로그램 제거를 캐시 정리 권한으로 확대하지 않는다.

HTML 제작실의 **내 작업물 → 저장공간 관리** 기본 목록은 원음 해시로 묶은 음악별 그룹이다. 음악을 펼쳐 프로젝트·버전·모션그래픽을 포함한 제작 폴더·관리 cache·미관리 용량·용도·핀·정리 이력을 확인한다. `storage:overview`은 기본적으로 마지막 완료 스캔을 쓰고, `refreshWorkspace:true`일 때만 작업 폴더 전체를 메타데이터로 다시 집계한다. `storage:tracking`의 관리/도구 영역은 미연결 제작물로 취급하지 않고 보호된 관리 영역으로 표시한다. 실제 소유 근거가 없는 폴더도 숨기거나 자동 삭제하지 않으며 소유권 미확인·보호로 표시한다. 새로 고침은 파일을 삭제·이동·재생성하거나 현재 자동 정리 정책을 바꾸지 않는다. 임시 검증 프로젝트·Git과 스캔 상세는 기타 관리에서 확인한다. UI의 전체 범위는 Road Music 작업 폴더와 등록된 프로젝트이며 컴퓨터 전체가 아니다.

**자동 일괄 정리**는 `storage:sweep-preview`로 전체 스캔과 계획을 먼저 만든 뒤 `storage:sweep-cleanup --confirm`으로 실행한다. 기본은 등록된 재생성 캐시와 검증된 과거 설치 복제본이며, 과거 제작·참조 자료·최종본 외 제작 자료와 AI M/V 최종본은 자동 포함하지 않는다. 사용자가 이미 정리를 맡긴 범위는 미리보기의 실제 대상·보호 상태를 검사한 뒤 실행하며 같은 승인을 반복해서 요청하지 않는다. `storage:overview`는 음악별 연결과 기타 자료를 구분하는 조회 명령이다.

## AI M/V 프로젝트 전체 정리

사용자가 M/V 결과·애니매틱까지 프로젝트 전체 정리를 요청하면 [AI M/V 전체 정리](references/mv-project-removal.md)를 읽는다. `storage:mv-list`의 검증된 프로젝트 ID를 음악별로 모아 최신 전체 스캔으로 계획한다. 전체 삭제 범위와 외부 원본 보존을 확인하고 `storage:mv-cleanup --confirm` 또는 명시 ID가 포함된 일괄 계획을 사용한다. 이름만 MV인 임의 폴더나 다른 음악의 Showreel 결과를 덧붙이지 않는다. 모델·앱·외부 원본 음악은 보호하고 삭제 요약과 입력 해시를 프로젝트 밖에 남긴다.

완료 보고는 실제 회수 용량, 삭제/건너뜀, 보존 대상, 남은 예산 경고와 자동 정리 범위를 짧게 알린다. 파일 검사만 했다면 실제 음악·영상 생성 검증과 구분한다.

## 프로젝트·음악 그룹 제거

프로젝트 또는 음악 그룹 삭제는 일반 캐시 정리가 아니다. `storage:project-remove-preview` 또는 `storage:group-remove-preview`의 일회용 계획에서 canonical 완성 파일 포함 여부·공유 원음·활성 lease·핀·외부 경로를 확인하고, 받은 `planId`만 `storage:entity-remove --confirm`으로 실행한다. 성공한 파일 처리 뒤에만 해당 live 소유권·경로·이벤트를 프로필 SQLite에서 제거한다. 적용 중 중단된 제거는 같은 계획 ID의 `storage:entity-recover --confirm`에서 격리 파일·원래 경로·SQL 상태를 다시 검증해 복구하며, 불일치·변조는 fail-closed로 격리를 보존한다. 공유·활성·핀한 자산, 모델·프로그램, 외부 원음은 보호하며 제거 범위를 임의로 넓히지 않는다.

명령별 예시·기존 작업 이전과 폴더 구조는 [운영 계약](references/workflow.md)을 필요한 때 읽는다.

## 완성본 전용 Output 구조 전환

기존 Output·미연결 제작 폴더를 새 구조로 옮기거나 정리해야 할 때는 [완성본 전용 구조 전환](references/final-output-structure.md)을 읽는다. 이 경로는 등록 완성본·원음·현재 모델·활성 작업을 보존하는 별도 일회용 계획이며, 자동 일괄 정리에 포함하지 않는다.

## 기존 제작·패키지 캐시 이전

등록 프로젝트의 관리 밖 picture/parts 또는 현재 trusted workspace의 검증 완료 로컬 패키지 ZIP을 정리해야 할 때만 [레거시 캐시 채택](references/legacy-cache-adoption.md)을 읽는다. `storage:legacy`가 해당 producer 프로필·납품·receipt·참조·열린 파일·symlink 검증을 거쳐 반환한 후보만 `storage:adopt-preview`와 확인된 `storage:adopt`로 관리 캐시에 옮긴다. 일반 draft·qa·tmp·스토리보드·임의 ZIP이나 이름만 cache인 자료는 채택하지 않는다. 채택 뒤 삭제는 별도 `storage:preview`·`storage:cleanup` 계획으로 수행하며, 사용자가 이미 이전 또는 정리를 요청한 범위는 다시 묻지 않는다.

공통 제작실의 제작 자료 ZIP과 원가사·자막별 연결, 행별 싱크 검수 기록 및 `feedback-history.jsonl`은 보존 대상이다. 상태/명령 참고 화면은 조회만 하며 세션 종료나 화면 열기를 작업 완료·정리 승인으로 보지 않는다.

## 과거 공용 영상 캐시 유지보수

사용자가 재시작과 공용 캐시 정리를 요청한 경우 현재 프로필의 `service:status`·`queue:list`에서 생성/대기/렌더/녹음/설치/이동/준비 작업이 없는지 확인한다. `service:stop`에는 강제 중단하는 `--confirm`을 붙이지 않는다. 기존 PID 종료를 확인하고 같은 설치·데이터로 재시작한다. 다른 프로필이나 독립 제작실 서버는 유지한다.

새 앱의 공개 `video:cache`가 idle 예약으로 검증한 과거 생성물만 미리보기하고 `video:cache-clear`에 반환된 `planId`와 `--confirm`을 전달한다. 계획은 같은 프로세스·15분·1회용이며 파일 변경 시 거부된다. 알 수 없는 파일·symlink는 보호한다. 공개 기능이 없는 설치본에서는 셸 삭제로 우회하지 않는다. 정리 감사 `video-cache-cleanup.jsonl`과 기존 큐 실패/복구 기록을 보존한다. 새 렌더는 곡/프로젝트의 관리 캐시를 사용하며 공용 폴더를 다시 만들지 않는지 확인한다.

## 작업 폴더의 과거 잔재 정리

프로젝트 관리 캐시가0B여도 전체 작업 폴더가 비어 있다는 뜻은 아니다. Git pack·옛 설치 검증 복제본·검증 가능한 과거 영상 버전·프레임 증거·완성 뒤 비최종 제작 자료를 구분한다. 사용자가 작업 폴더 유지보수를 요청하면 [작업 폴더 유지보수](references/workspace-maintenance.md)를 읽고 공개 `storage:maintenance-*`와 HTML의 **기타 관리 → 과거 제작·참조 자료/최종본 외 제작 자료** 기능을 사용한다. 전체 스캔 뒤 `scope:artifacts` 또는 `scope:retirement`와 목록의 `candidateIds`를 명시한 계획만 실행한다. 현재 프로그램/모델/최종 결과물/필요 이력은 계속 보호하고, 모델 제거는 별도 명시 작업이다. 다른 종류의 큰 파일까지 정리 권한을 확대하지 않는다.

전체 사용량을 설명할 때에는 음악·영상·모델·프레임·패키지·Git을 나누고, 같은 inode인 모델 경로를 두 번 합산하지 않는다. 프로젝트 밖의 모델 제거로 확보한 공간은 작업 폴더의 감소량과 따로 보고한다. 사용자가 특정 모델 제거를 명시했을 때도 그 모델의 가중치·전용 다운로드 캐시와 공유 Python/실행 도구를 구분한다. 테스트에서는 설치 모델을 재사용하고 별도 데이터 프로필의 서비스가 종료된 뒤 그 프로필의 브라우저 캐시만 정리하며, 샘플 원음·영상과 최소 생성·정리 기록을 보존한다.

HTML 정리 확인은 현재 표시한 계획 하나에만 연결한다. 취소·Escape·새로고침·프로젝트 전환 후에는 이전 계획을 실행하지 않으며 새 미리보기가 필요하다. 정리 실행을 시작한 뒤에는 닫기로 취소된 것처럼 안내하지 않고 완료·실패를 확인한다. 느린 이전 응답이나 중복 클릭이 다른 삭제 범위로 이어지지 않는지 검수한다.
